# The Weekly Table

A shared lunch & dinner planner for two, running entirely on Cloudflare's free tier.

| Layer | What |
|---|---|
| Frontend | React 19 + Vite + TypeScript, [shadcn/ui](https://ui.shadcn.com) on Tailwind v4, TanStack Query |
| API | [Hono](https://hono.dev) on Cloudflare Workers (`/api/*`) |
| Database | Cloudflare D1 (SQLite) via [Drizzle ORM](https://orm.drizzle.team) |
| Sign-in | Cloudflare Access (Zero Trust), email one-time PIN; no login code in the app |
| Hosting | One Worker serves both the built React app (Workers static assets) and the API |

```
src/        React app (components/ui = shadcn components)
worker/     Hono API, Access JWT check, Drizzle schema
shared/     Date helpers and types used by both sides
migrations/ SQL migrations generated by drizzle-kit, applied by wrangler
test/       API + auth tests, run inside the real Workers runtime
```

## Local development

```bash
pnpm install
cp .dev.vars.example .dev.vars    # sets the pretend signed-in user
pnpm db:migrate:local             # creates the local D1 database
pnpm dev                          # http://localhost:5173
```

There is no Cloudflare Access locally, so the API treats you as `DEV_AUTH_EMAIL`.
That shortcut only works on `localhost`; on any real hostname a valid Access token is required.

```bash
pnpm test        # API and auth tests in workerd with a throwaway D1
pnpm typecheck
```

Add more shadcn components with `pnpm dlx shadcn@latest add <component>`.

### Changing the database

1. Edit `worker/db/schema.ts`
2. `pnpm db:generate` writes a new SQL file to `migrations/`
3. `pnpm db:migrate:local`, and `pnpm db:migrate:remote` when deploying

## First deploy

All of this is free. A custom domain is optional.

1. **Log in and create the database**
   ```bash
   pnpm exec wrangler login
   pnpm exec wrangler d1 create homeapp
   ```
   Paste the printed `database_id` into `wrangler.jsonc`.

2. **Create the tables and deploy**
   ```bash
   pnpm db:migrate:remote
   pnpm run deploy
   ```
   The app is now at `https://homeapp.<your-subdomain>.workers.dev`. Until step 3 the API
   refuses every request, because Access isn't configured yet.

3. **Put Cloudflare Access in front of it**
   - Dashboard → Workers & Pages → `homeapp` → Settings → Domains & Routes →
     enable **Cloudflare Access** on the `workers.dev` route (and on preview URLs).
     Or, with a custom domain: Zero Trust → Access → Applications → add a self-hosted app for it.
   - Set the policy to **Allow** with an **Emails** rule listing your two addresses.
     Login method: **One-time PIN** (emails a code; nothing to set up).
   - Copy the application's **Audience (AUD) tag** and your **team domain**
     (`<team>.cloudflareaccess.com`, under Zero Trust → Settings) into `vars` in
     `wrangler.jsonc`, then deploy again.

4. **Optional second gate.** The Worker checks this as well as Access:
   ```bash
   pnpm exec wrangler secret put ALLOWED_EMAILS   # e.g. you@x.com,sophia@y.com
   ```

5. **Optional auto-deploy.** Dashboard → Workers & Pages → `homeapp` → Settings → Builds →
   connect this GitHub repo. Build command `pnpm run build`, deploy command `pnpm exec wrangler deploy`.

### How sign-in works

Access sits in front of the whole hostname. Anyone not signed in is sent to Cloudflare's login
page before they reach the app. Signed-in requests carry a signed JWT
(`Cf-Access-Jwt-Assertion`), which `worker/auth.ts` verifies against your team's public keys,
issuer and AUD. So the API stays protected even if a route is ever left uncovered by Access.
"Sign out" goes to `/cdn-cgi/access/logout`.

## Free-tier headroom

Workers free plan: 100k requests a day. D1 free: 5M row reads and 100k writes a day.
Access: free up to 50 users. Two people planning meals, with the page polling every 20 seconds
while it's open, uses a tiny fraction of that.
